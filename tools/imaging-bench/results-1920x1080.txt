# JMH results for :tools:imaging-bench — the source of truth for the performance table in
# public/docs/imaging_examples.md. Regenerate the page with:
#     python3 tools/imaging_bench_doc.py --write
#
# Measured 2026-07-27 (10:26–10:50) on nightly/2026-07-27/1-imaging-simd-perf, after the
# vector-kernel work: the unrolled stencil accumulator, pyrDown's fused polyphase decimation,
# boxBlur's row-wise running sums, and bilateral's tabulated range weight.
#   machine : Apple Silicon, 10 cores (8 performance + 2 efficiency), 64 GB
#   JVM     : GraalVM CE 25.0.2, C2 host JIT (-XX:+EnableJVMCI -XX:-UseJVMCICompiler),
#             --add-modules jdk.incubator.vector
#   JMH     : 5 warmup + 10 measurement iterations of 1s, 3 forks (Cnt 30), average time
#   image   : 1920x1080 (2.07 Mpx), CV_32F on both sides, OpenCV 4.9 pinned to one thread
#   load    : load average 5.14 at the start of the run and 6.19 at the end, over 23m31s, with the
#             benchmark JVM the only busy process. Quieter than that sounds: the JMH fork is
#             single-threaded, so about 1 of 10 cores was ours.
#
# THREADING. Nothing here is multithreaded, on either side. OpenCV is pinned with setNumThreads(1)
# because our implementation is single-threaded, and no arm in this file uses more than one thread.
# There is no parallel arm; if one is ever added it must be named and labelled separately rather
# than quietly compared against a single-threaded baseline.
#
# READING THIS AGAINST THE PREVIOUS RUN. The `opencv*` arms are unchanged third-party code, so they
# serve as the control — and they read 3.3% slower on average here than in the 2026-07-27 pre-work
# run (worst +11.2%: opencvLaplacian 1.450 -> 1.612). That is machine state, not anything we did.
# So when comparing an ours-vs-OpenCV ratio in this file against a ratio in the older one, roughly
# 3% of any apparent improvement is drift. The within-run ratios are self-consistent and are the
# numbers to trust.
#
# NOISIEST ARM. oursBilateral reads ± 95.184 on 749.076 — 12.7% relative, far wider than anything
# else here and wide enough that its ratio should be read as "about 1.2x". The same arm 25 minutes
# earlier gave a minimum of 719.7 ms over 8 iterations. Every other arm is under 3% relative error.
#
# Correctness cross-check performed once per trial; the run fails if these diverge:
#   gaussian  simd-vs-scalar 1.19e-7   simd-vs-opencv 2.38e-7
#   boxBlur   ours-vs-opencv 7.84e-6   (was 9.89e-6 before the running sums were restructured)
#   laplacian ours-vs-opencv 0.0
#
# oursBoxBlurViaKernel is a decision arm, not a published row: it computes the same radius-2 mean
# via convolveSeparable(boxKernel1D(2)) to test whether the O(1) running sum is worth it at small
# radius, because a live-box timing had said it was not. It is — 2.598 against 3.181 — so boxBlur
# keeps the running sum at every radius.
