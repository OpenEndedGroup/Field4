# Steam Audio → Kotlin/FFM bindings — scope

Target: `afield.four.audio.steamaudio`, Kotlin/JVM, JDK 25+, Panama FFM.
Upstream: Steam Audio **4.8.1** (released 2026-02-11), Apache-2.0.

For using the API rather than reading about how it got here, start with
[STEAMAUDIO_INTEGRATION.md](STEAMAUDIO_INTEGRATION.md).

## Where this lives

Field is the only home for this code. It was developed in a separate checkout, now retired, and
folded in here the way Ceres and TetGen are rather than as a submodule: the code is in Field's
own tree and its build graph, and only the binaries are fetched.

| | |
|---|---|
| L1, jextract output | `src/jvmMain/java/afield/four/audio/steamaudio/raw/` |
| L2, the Kotlin API | `src/jvmMain/kotlin/afield/four/audio/steamaudio/` |
| Demos and probes | `src/jvmMain/kotlin/afield/examples/steamaudio/` |
| Tests | `src/jvmTest/kotlin/afield/four/audio/steamaudio/` |
| The pin, notices and header | `native/steamaudio/` |
| Fetch script | `tools/fetch_steamaudio_natives.py` |

`./gradlew fetchSteamAudioNatives` unpacks this host's libphonon into `build/steamaudio`,
verified against `native/steamaudio/checksums.txt`. Nothing binary is committed.
`-PsteamaudioLibrary=<path>` overrides it, which is the escape hatch for a libphonon you built
yourself (Linux arm64 being the case that needs one).

Not wired into `check`, for the reason TetGen and Ceres are not: a fresh clone has no network
guarantee. The tests skip with a stated reason via `SteamAudioNatives.isAvailable` instead, so
`check` is green on a clone that has never fetched the binaries and honest about why. The
pure-arithmetic cases -- the handedness invariants, the segment transform, the Ambisonic channel
counts -- deliberately keep running, since they need no library.

`src/jvmMain/java` is compiled at release 24 to match `compileKotlinJvm`'s `jvmTarget`; Gradle
rejects a mismatched pair outright. FFM has been final since 22, so this costs the bindings
nothing.

Two things from the retired checkout did **not** come across, both because they presuppose
publishing these bindings as an artifact, which Field does not do:

- `module-info.java`. Adding a module descriptor to `src/jvmMain/java` would make the whole of
  Field's jvmMain a named module. Field runs in the unnamed module and passes
  `--enable-native-access=ALL-UNNAMED` throughout, so this is a change to Field, not to the
  bindings, and belongs with a decision to publish.
- `PackagingVerifier` is present but has no Gradle task. It checks the classpath-resource
  extraction path with no `steamaudio.library.path` set, which is the path a published natives
  jar would take. Every Field task sets that property and there is no natives jar, so there is
  nothing here for it to verify.

## Measured facts about the API

- **216 exported functions** in `phonon.h`; jextract binds **216/216** (100%).
- **62 structs**, **26 enums**, **31 opaque handle types**, **13 function-pointer types**.
- **No unions, no bitfields, no `long double`, no varargs.** Only fixed-width scalars,
  fixed-size arrays, and pointers. `IPLsize` is the only platform-dependent type (8 bytes
  on every target we care about).
- **All 62 struct layouts are byte-identical** across `arm64-apple-macos`,
  `x86_64-apple-macos`, `x86_64-linux-gnu`, `x86_64-windows-msvc` and `aarch64-linux-gnu`
  (verified by diffing `clang -fdump-record-layouts-complete` across all five ABIs).
  → **One generated binding set works on every platform.** No per-platform codegen.
- `IPL_NUM_BANDS == 3` in the shipped binaries (confirmed at runtime).
- The object model is extremely regular: every audio effect has exactly 7 functions
  (`Create`/`Retain`/`Release`/`Reset`/`Apply`/`GetTailSize`/`GetTail`). 60 of the 216
  functions are `Retain`/`Release` pairs. This regularity is worth exploiting.

## Architecture

Three layers:

- **L0 `native/`** — vendored header + prebuilt libs. Done.
- **L1 `afield.four.audio.steamaudio.raw`** — jextract output, 77 files / 32.5k LOC,
  checked in, marked internal. Regenerated by a Gradle task, never edited by hand.
- **L2 `afield.four.audio.steamaudio`** — the hand-written idiomatic Kotlin API. This is
  the actual work.

Generated with **no `-l` flag**, so the lookup preamble is
`loaderLookup().or(defaultLookup())` — meaning we control loading via `System.load(absolutePath)`.
That is what makes jar-extracted natives possible; jextract's default `libraryLookup("phonon")`
would hard-fail since it only consults the OS loader path.

## Work breakdown

### 1. Native loading (`SteamAudioNatives`) — small, fiddly
Detect os/arch → extract from classpath resource to a checksummed cache dir → `System.load()`
the absolute path. Must handle: repeat loads in one JVM, multiple classloaders, read-only
temp dirs, and an override for loading from a plain directory.
Windows additionally needs `TrueAudioNext.dll` + `GPUUtilities.dll` resolvable *before*
`phonon.dll` — load order matters.

### 2. Handles and lifetime — medium, this is where the bugs live
31 opaque types. The C convention is that `Create` takes `IPLXxx*` out-param and
`Release` takes `IPLXxx*` and **nulls the caller's slot**, so each wrapper needs to own a
stable 8-byte slot, not just a pointer value.
Design: `sealed class SteamAudioObject : AutoCloseable`, deterministic `close()`, plus a
`Cleaner` safety net. Refcount semantics (`Retain`) exposed only where the API genuinely
needs shared ownership (e.g. `IPLScene` held by both simulator and static meshes).

### 3. Enums and flags — small, but two real traps
- 5 flag-style enums (`IPLContextFlags`, `IPLDirectEffectFlags`, `IPLSimulationFlags`,
  `IPLDirectSimulationFlags`, `IPLReflectionsBakeFlags`) must be `@JvmInline value class`
  with `or`/`in` operators — **not** `enum class`, they're bit-OR'd.
- `IPLSIMDLevel` has **aliased values**: `IPL_SIMDLEVEL_NEON == IPL_SIMDLEVEL_SSE2 == 0`.
  A naive `fromValue` map collides. Needs explicit handling.

### 4. Structs — medium, split by call frequency
- *Cold* (settings, created once): Kotlin `data class` + `writeTo(MemorySegment)`.
- *Hot* (`IPLBinauralEffectParams`, `IPLDirectEffectParams`, `IPLSimulationInputs`, …,
  written every audio block): **must be zero-allocation**. Arena-backed mutable views with
  `var` properties writing straight through to native memory. No boxing, no per-block alloc.
- `IPLVector3` / `IPLCoordinateSpace3` / `IPLMatrix4x4`: small value types + read/write helpers.

### 5. `IPLAudioBuffer` — medium, and the most performance-critical piece
`{ int numChannels; int numSamples; float** data; }` — deinterleaved, caller-allocated.
Design: one contiguous arena-allocated sample block plus a channel-pointer array, wrapped as
`AudioBuffer`. Bridges to `FloatArray` / `FloatBuffer`. Reuse the SDK's own
`iplAudioBufferInterleave` / `Deinterleave` / `Mix` / `Downmix` / `ConvertAmbisonics` rather
than reimplementing them in Kotlin.

### 6. Callbacks (upcalls) — medium, risky in one place
13 function-pointer types via `Linker.upcallStub`. Two very different tiers:
- Cold: `IPLLogFunction`, `IPLProgressCallback`, `IPLAllocateFunction`/`FreeFunction`.
- **Hot**: `IPLClosestHitCallback` / `IPLAnyHitCallback` / their batched variants, for
  `IPL_SCENETYPE_CUSTOM`. These are invoked from Steam Audio's *own* ray-tracing threads at
  very high rates. Cost of JVM thread attachment and upcall overhead is the concern; must be
  allocation-free. If custom scenes aren't needed, this tier can be deferred cheaply.

### 7. Real-time safety surface — small, mostly design + docs
`iplSimulatorRunReflections` / `RunPathing` are blocking and must never touch the audio
thread; the `*Apply` calls are the audio-thread-safe subset. The Kotlin API should make that
split obvious rather than leaving it to documentation.
Note `IPLAudioEffectState` (`TAIL_COMPLETE`/`TAIL_REMAINING`) returned by `*Apply` is **not**
an error code and must not be thrown on — unlike `IPLerror`, which should throw
`SteamAudioException` on cold paths.

### 8. JPMS `module-info` — small, but the real "JVM 25 and above" ask
JDK 25 *warns* on restricted native access from the unnamed module; this is scheduled to
become *denied by default*. Shipping a named module lets consumers write
`--enable-native-access=afield.four.audio.steamaudio` instead of `ALL-UNNAMED`. Worth doing now.

### 9. Tests + CI — medium
- Create/release lifecycle test per handle type, with a counting custom allocator to assert
  zero leaks.
- **Layout-guard test**: assert generated layouts against the checked-in reference table
  (`src/test/resources/phonon-4.8.1-layouts.txt`, 62 records) so a future jextract or SDK
  bump can't silently shift a field.
- Golden-output test: run a binaural effect over a known impulse, compare to a stored buffer.
- CI across macOS / Linux / Windows.

## Decisions I need from you

1. **API scope.** Bind all 216, or start with a core subset? A natural first cut is to defer
   the GPU/accelerator paths (`Embree`, `RadeonRays`, `TrueAudioNext`, `OpenCL` — ~18
   functions) and the bake/probe system (`ProbeArray`, `ProbeBatch`, `ReflectionsBaker`,
   `PathBaker` — ~24 functions), leaving ~174 for the first pass. L1 binds everything
   regardless; this is only about how much of L2 gets a hand-written wrapper.

2. **linux-arm64.** Valve ships **no aarch64 Linux binary** — only `linux-x64` and
   `linux-x86`. So "all three platforms" currently means macOS (universal x64+arm64),
   Windows x64, Linux **x64 only**. Options: (a) accept that, (b) build libphonon from
   source for aarch64 (it's Apache-2.0 + CMake, but a real side quest). I verified the
   struct layouts already match aarch64-linux, so the bindings are ready either way.

3. ~~**Natives packaging.**~~ **Decided: fetch-on-build.** Nothing binary is committed. The
   release zip is pinned by SHA-256, as is every file taken out of it, and only this host's
   platform is unpacked. The zip is cached by `tools/native_download_cache.py` outside the build
   directory, so `clean` costs a re-extract rather than a 173 MB re-download. Classified
   artifacts remain the right answer if these bindings are ever published outside Field.

4. **Layer 2: hand-written or generated?** Given how regular the API is (that uniform
   7-function effect pattern), a small codegen pass over the header could emit most of L2
   mechanically, with hand-written overrides for `AudioBuffer`, `Simulator` and `Scene`.
   Cheaper to maintain across SDK bumps; more upfront work than hand-writing.

## Notes / gotchas already banked

- `IPLEmbreeDeviceSettings` and `IPLRadeonRaysDeviceSettings` are `typedef void` in the
  shipped configuration (they're only real structs when those backends are compiled in).
  jextract skips them; their parameters are just `void*` — pass `NULL`.
- `IPLCALL` is `__stdcall` on `_WIN32`. Harmless for us: on Win64 `__stdcall` is the standard
  x64 convention. It would be a blocker only for 32-bit Windows, which JDK 25 doesn't ship.
- The dylib exports 362 `ipl*` symbols but only 216 are declared in the public header. We
  bind the declared 216; the rest are internal.
- `phonon_interfaces.h` is a C++ header (`namespace api`, virtual classes). Irrelevant to
  FFM — ignore it.
- macOS `libphonon.dylib` is a universal binary (x86_64 + arm64), so one file covers both Macs.

## Target use case (drives Layer 2 priorities)

Full-quality spatial audio for a **lively, reverberative, cave-like space**: HRTF binaural
output, and a **dynamic arrangement of planes** that reflect and absorb, with sources acting as
sonic probes radiating into largely empty darkness.

That pushes the following to the front of Layer 2, ahead of the rest of the surface:

1. **`Simulator` / `Source` with an explicit thread split.** `iplSimulatorRunReflections` is
   the expensive blocking call and must live on its own thread, never the audio callback.
   The API should make that split structural rather than a documentation note.
2. **Dynamic geometry.** `InstancedMesh.updateTransform` + `Scene.commit` is the per-frame
   path for moving planes; `StaticMesh.add`/`remove` for appearing and disappearing ones.
   `commit` cost is what will bite, so it needs to be explicit and batchable — one commit per
   frame covering many plane moves, not one per plane.
3. **Reflections at quality.** `CONVOLUTION` and `HYBRID` reflection types, long `maxDuration`,
   high ray counts, plus `ReflectionMixer` to keep per-source convolution affordable.
4. **Tail handling as a first-class concern.** In a long-decay space, `getTailSize` / `getTail`
   are not an afterthought: when a source stops or a plane moves away, the tail must flush
   correctly or the reverb audibly truncates.
5. **The full binaural chain.** Direct → `BinauralEffect`; reflections → Ambisonics →
   `AmbisonicsDecodeEffect` in binaural mode. Both need to run allocation-free per block.

Two consequences worth recording:

- **Baking and probes are largely inapplicable here.** Baked reflection data assumes static
  geometry; with planes moving every frame, reflections must be simulated live. Probes/baking
  still get bound (full surface was requested), but they are not on the critical path — the
  exception being a static outer shell, if the space has one.
- **A quad/plane helper earns its place in the API.** The geometry primitive in this world is a
  four-corner plane with a material, not a general mesh, so `StaticMesh.plane(...)` and a
  material palette are worth having as first-class conveniences.

### Two things worth keeping

**A parked panel was sitting on the source corridor.** The first cave render showed the direct
path collapsing 39 dB partway through the *distance* movement. Steam Audio was correct: my
resting-panel layout put a 5x5 concrete slab at exactly `(0, 1, −9)`, and the receding source
passed behind it. Diagnosed by computing panel positions against the source path, not by
guessing. `panelTransform` now keeps all four panels off the `x = 0` corridor and occlusion is
confined to movement 4, where it is the subject.

**Analysis windows have to match the physics being measured.** Three separate times, a
measurement looked like a bug and was not: broadband RMS hid frequency-dependent ILD in the
orbit demo; a 30 ms "direct" window caught the 21 ms floor reflection; and a 30–60 ms "early"
window missed panel reflections entirely because geometry at 2.8 m reflects within 9 ms and
fuses with the direct arrival. In every case the audio was right and the measurement was wrong.

**Direct path carries no propagation delay.** Steam Audio's `DirectEffect` applies gain and
spectrum but not time-of-flight, while `ReflectionEffect` honours the simulated `delay`. So
direct arrives at HRTF latency (~6 ms) while reflections arrive late. This is the upstream
idiom, not a binding bug — but an application wanting true time-of-flight on the direct path
must add that delay itself.

## 2D geometry support, and a mirroring bug the tests caught

### The game frame

Geometry in **xy**, listener translating in xy and rotating about **z**, both ears in the plane
of the geometry. Right-handed, `+x` right, `+y` up the screen, `+z` out of the screen.

`World2D` maps game `(gx, gy, gz)` to world **`(gx, gz, -gy)`**. Steam Audio's up is `+y`, so
the game's up (`+z`) must become world `+y`; right-handedness then forces game `+y` to world
**`-z`**, not `+z`.

**The obvious mapping is wrong.** `(gx, gy) -> (gx, height, gy)` is orientation-reversing under
these conventions and silently swaps the listener's ears. Levels, reverb, distance and
occlusion all stay correct — only left and right invert, which is exactly the kind of failure
that ships.

### The bug

`CoordinateSpace3.lookingAt` computed `right = up cross forward`, which for Steam Audio's
canonical frame (`-z` ahead, `+y` up) gives `(-1, 0, 0)` while `CoordinateSpace3.IDENTITY`
declares `(1, 0, 0)`. The two constants in the same file disagreed. Fixed to
`right = forward cross up`, and pinned by `CoordinateSpaceHandednessTest`:

- `lookingAt` on the canonical direction now reproduces `IDENTITY`
- `right cross up == -ahead` holds for every facing (the right-handedness invariant)
- axes are orthonormal

`World2DHandednessTest` then checks the *rendered audio*, not the maths: it puts an impulse
through the real binaural chain and asserts which ear leads and which is louder, for east, west,
ahead, behind, a listener turned around, and twelve azimuths round the circle. 14 tests, all
passing.

The cave demo used `lookingAt`, so its earlier render was mirrored. Its published measurements
(RT60, distance, occlusion) are level-based and unaffected; it has been re-rendered regardless.

### API added

`World2D` (mapping, `point`, `listenerFacing`, `listenerAtAngle`) · `WallSegment` ·
`WallSet` (extrudes segments to quads, caps both ends double-sided, `triangleCount` for
budgeting) · `MovableWall` (an `InstancedMesh` over a unit quad; `moveTo(x0, y0, x1, y1)`,
`hide`) · `MovableWall.sharing` for many movable segments over one shared quad ·
`Matrix4x4.times`, `transformPoint`, `rotationX/Y/Z`, non-uniform `scale`.

**Caps are not optional.** Extruded line segments alone form an open-ended box; rays escape
through the gap and the reverb collapses. `WallSet` caps by default, double-sided so a
backwards winding cannot make a cap invisible from inside.

### Front/back confusion is the real localisation limit here

With both ears in the geometry plane every source sits at zero elevation, so the HRTF's
elevation dimension is unused and front/back becomes ambiguous — a source ahead and one behind
produce near-identical ILD and ITD, measured at roughly 0 dB for both. Humans resolve this with
small head movements; if facing snaps in discrete steps that cue is absent, and sources behind
will often be heard as in front. Worth designing around: smooth rotation, and leaning on reverb
and occlusion differences rather than direction alone.

## Measured: what geometry actually costs

`./gradlew geometryBenchmark`

| | result |
|---|---|
| commit after moving 4 instances | **0.01–0.07 ms**, and *falls* as triangles rise (1.2k → 76.8k) |
| add/remove + commit | at the timer floor |
| deferred into the next ray query? | **no** — a run after move+commit costs the same as one after no change (differences are noise, one negative) |
| `runReflections` | 10–15 ms at 4096 rays / 16 bounces, across a 64x range of geometry size; 32 ms at 8192/32; 54 ms at 16384/32 |
| initial `StaticMesh` build + first commit | 1.8 ms at 1.2k triangles → ~52 ms at 76.8k |

**A mixed static/dynamic scene needs no special arrangement.** Steam Audio maintains the
acceleration structure incrementally, so static geometry can go straight into the scene with
the dynamic pieces as instanced meshes. Nesting static geometry in a sub-scene is worth doing
for *reuse* — instancing one room shape many times — but it is not a commit-cost optimisation,
which is what I first assumed and the numbers disproved.

For a 2D game this is comfortable: a few hundred wall segments is a few hundred triangles, well
under the smallest case measured. **Budget the ray count, not the geometry.** The one cost that
does scale is the initial build — pay it at area load, not when an area becomes visible.

## Pathing — done and measured

`./gradlew pathingDemo` renders `build/demo/pathing.wav`: a 2D room split by a wall with a
doorway at one end, listener facing the wall, source directly behind it. Three movements —
same room, occlusion only, then pathing enabled on identical geometry.

### Measured

| | level | balance (R−L) | high-vs-low tilt |
|---|---|---|---|
| same room | −32.9 dB | +0.17 dB (centred) | +9.8 dB |
| occluded only | **−88.5 dB** | +0.16 dB (centred) | +9.7 dB |
| occluded + pathing | **−54.9 dB** | **−5.83 dB (left)** | **−8.6 dB** |

Three independent confirmations that pathing is doing real work:

1. **+33.6 dB** over occlusion alone. Through concrete, transmission is effectively inaudible
   at −88 dB; the pathed route is clearly present.
2. **The sound moves.** Occluded, it sits dead ahead — that is where the wall is. With pathing
   it shifts **5.8 dB to the left**, which is where the doorway is (listener faces east, doorway
   is north-east). That relocation is the point of pathing.
3. **It arrives dark.** Simulated `pathEQ` is `0.709 / 0.360 / 0.208` across low/mid/high — a
   monotonic tilt, because low frequencies diffract round a corner and high ones do not. The
   rendered high-vs-low tilt drops 18.4 dB relative to the unobstructed case.

Bake cost for this room: 98 probes at 1.5 m spacing, 51 KB of pathing data, sub-second.

### The dependency that makes pathing different

Every other effect here is purely geometric at runtime. **Pathing is not**: it searches a
precomputed probe-to-probe visibility graph, so it needs `ProbeArray` → `ProbeBatch` →
`PathBaker.bake`, and it renders silence without them. The demo `check`s for probes and for
non-zero baked data precisely because a silent path effect is otherwise indistinguishable from
a wiring mistake.

Two consequences for moving walls:

- **The graph assumes bake-time geometry.** Pathing will route through a doorway a moving wall
  has since closed, and will not find one it has since opened. Options: re-bake the area
  (not per-frame), bake with the door open and let occlusion and transmission handle the closed
  case, or keep connectivity-changing geometry out of the graph and let reflections carry it.
- Baking is tool-time. `PathBaker.bake` blocks; run it at area load or offline and
  `ProbeBatch.save` the result.

`PathingVisualizationCallback` and `SimulationSharedInputs.setPathingVisualizationCallback`.

`hasNoPath()` is the diagnostic worth knowing: it distinguishes "pathing found nothing" from
"pathing found a quiet route", which are the two failure modes that sound identical.

**`PathingVisualizationCallback`** receives every probe-to-probe segment the search examines,
with an `occluded` flag. In a 2D game you can draw these straight onto the map, which turns a
silent path effect into a visible picture of which probes cannot see each other. Convert back
with game `x` = world `x`, game `y` = **minus** world `z`.

### A latent bug fixed alongside

`SpeakerLayout.CUSTOM` holds a raw pointer to its speaker-direction array, which upstream does
not document as being copied. Both `PathEffect` and `AmbisonicsDecodeEffect` were allocating
that array in a scratch arena that closed as soon as creation returned, leaving a dangling
pointer for the effect's lifetime. Standard layouts were unaffected (their pointer is null).
Both effects now own a shared arena for the directions when the layout is custom, released in
`onClosed`.

## Leak tests, binaural quality, packaging

34 tests, all passing: `LeakTest` (19), `World2DHandednessTest` (6), `SmokeTest` (5),
`CoordinateSpaceHandednessTest` (3), `AllocationReportTest` (1).

### Leak tests

`MemoryAllocator` is now a public API -- installing one on the context routes every internal
Steam Audio allocation through your code, which is also how an audio engine can keep allocation
off the critical path. `CountingAllocator` (test-only) implements it over libc `malloc`/`free`
with manual alignment, since `aligned_alloc` is C11 and `_aligned_malloc` is Windows-only.

The assertion is deliberately **not** "outstanding memory returns to zero": a context keeps
caches and thread scratch for its own lifetime. Each test creates and closes a batch to
establish a baseline, then repeats 40 more times and asserts the total returns to it. A real
leak grows without bound; a one-off warm-up is absorbed.

Measured footprints (`./gradlew test --tests '*AllocationReport*'`):

| operation | allocations | bytes outstanding after |
|---|---|---|
| `Hrtf.default`, left open | 57 | **15,292,964** |
| `Hrtf.default`, create+close | 57 | **0** |
| `BinauralEffect`, create+close | 80 | **0** |
| `ReflectionEffect` 3 s order 2 | 55 | **0** |
| `Scene` + 4-wall room | 19 | **0** |
| `Simulator` | 8 | **0** |

Every create+close pair returns exactly its memory. Also covered: `retain` needs a matching
`close`; a retained object survives the original closing and still renders; double-close
decrements once; use-after-close throws `IllegalStateException` rather than segfaulting.

The **~15 MB HRTF** is the number to design around: share one per listener, never one per source.

### Binaural quality — measured, `./gradlew binauralQuality`

**Use `BILINEAR` interpolation.** `NEAREST` produced only **14 distinct ILD values** across 46
azimuth samples with a worst step of 6.46 dB; `BILINEAR` gave 45 distinct values and 1.76 dB.
That step is an audible zipper on a moving source.

**Use Ambisonic order 2 for the reflected and pathed buses**, not order 1. Scored against direct
binaural rendering (the accuracy ceiling, 20.4 dB peak ILD):

| order | channels | ILD error | peak ILD reached |
|---|---|---|---|
| 1 | 4 | 7.05 dB | 11.5 dB — **57%** |
| 2 | 9 | 3.83 dB | 18.6 dB — **91%** |
| 3 | 16 | 2.95 dB | 19.4 dB — 95% |

Order 1 → 2 removes 46% of the error for 9 channels; 2 → 3 removes a further 23% and costs 16.
Order 1 is measurably blurry. **The cave demo's order 1 should be raised to 2.**

Keep `spatialBlend` at 1.0 (0.75 already loses 22% of the ear-balance cue), keep the direct path
on a `BinauralEffect` rather than folding it into the Ambisonic bus, and never binauralise twice
-- a binaural Ambisonic decode is already an HRTF render.

### A behaviour worth knowing: parameters are ramped across a block

Steam Audio interpolates parameter changes over the block rather than at sample zero, which is
what stops moving sources clicking. Consequence, measured directly: an Ambisonics encode given a
fresh direction and an impulse at **sample 0** emits *only* the omnidirectional component, every
directional component zero. Settle with one block of the new parameters first.

This invalidated the first version of the quality probe -- it reported every Ambisonic order as
identical, which read like "order does not matter" and was actually "my measurement never let
the direction take effect". Documented on `AudioEffect`, because it also affects one-shots
shorter than a block.

A second measurement trap, also fixed: onset-threshold ITD collapses to zero under `BILINEAR`,
because interpolation sums two responses with different delays so both ears show early energy.
Cross-correlation over a broadband impulse is the right instrument. ITD is *not* meaningful for
an Ambisonic decode at all -- the field is resynthesised from harmonics -- and the probe now
says so rather than implying a quality score.

**`module-info.java` ships**, exporting only `afield.four.audio.steamaudio` and keeping the
32k-line generated `raw` package encapsulated. Two bugs found by actually running it, not by
assuming it worked:

1. **`requires transitive kotlin.stdlib` was missing.** The module compiled without it and
   failed at the consumer with `ClassNotFoundException: kotlin.jvm.functions.Function0`.
   Transitive because Kotlin types appear throughout the exported API.
2. **`Class.getResourceAsStream` cannot see the natives jar.** It resolves against the calling
   class's *own module*, so a separately published natives jar is invisible — which is the
   whole point of publishing it separately. The loader now tries the class, then the class
   loader, then the context loader.
   (`src/jvmMain/kotlin/afield/four/audio/steamaudio/SteamAudioNatives.kt:325#readResource`).

the classpath.** They hold resources and no code, so nothing `requires` them, they are never
resolved, and their resources stay invisible. Verified all three arrangements; the one that
works keeps the library on the module path and the natives on the classpath. The failure now
produces a seven-line error saying exactly that. The natives jars also carry an explicit
`Automatic-Module-Name`, because the derived one collided with the library's own artifact id.

`./gradlew verifyPackaging` loads the built jars from a bare classpath with no system
properties, extracts from resources, and renders an impulse — so a layout/loader mismatch fails
our build rather than the consumer's runtime.

## Cave at Ambisonic order 2 — and a correction

`AMBISONIC_ORDER` in the cave demo is now **2** (9 channels), overridable with
`-Dsteamaudio.demo.order=1`, plus `-Dsteamaudio.demo.reflectionsOnly=true` to mute the direct
path so the reflected field can be compared in isolation.

### The measured benefit here is below the noise floor

I predicted a clear improvement on the strength of `binauralQuality`, which showed order 1
reaching only 57% of direct binaural's peak ear-balance against order 2's 91%. In this cave
that does not reproduce. Directional spread of the reflected field, order 1 versus order 2:
`+4%` early, `+20%` mid, `+46%` late, `-22%` tail — no monotonic pattern, and all on
standard deviations of 0.26–1.19 dB.

So I rendered order 1 **twice** as a control. Run A versus run B: `-1%`, `+11%`, `+27%`,
`-15%` — the same magnitude and the same sign pattern as the order difference. The two runs
are not even the same length (1787904 vs 1782784 samples). **The reflection simulation is
stochastic, and the order difference in this scene is indistinguishable from run-to-run
variance.**

Two reasons the probe's result does not carry over:

- **The probe measured a single point source encoded at a known direction** — the best case for
  Ambisonic order. A cave's late reverb is close to the worst case: a genuinely diffuse field
  has little direction to sharpen, so a higher order has little to represent.
- **`HYBRID` reflections synthesise the late tail with a parametric feedback delay network**,
  not by decoding spherical harmonics. Raising the order can only affect the convolved early
  portion, which is a minority of the energy in a 1.7-second decay. A `CONVOLUTION` reflection
  type would be order-dependent throughout.

### What this does not change

Order 2 stays the default. The controlled measurement of a directional source is real and
large, and it is the case that matters for early reflections off a nearby plane or a pathed
route through a doorway — both directional, both order-sensitive. 9 channels against 4 is a
modest cost at these ray counts, where `runReflections` dominates the budget.

What changed is the *claim*: order 2 is justified for directional content, **not** on the
strength of an audible improvement to diffuse cave reverb, which I asserted and then could not
demonstrate. Renders of both orders are provided, full mix and reflections-only, at identical
normalisation so they A/B directly.

### Worth following up

If diffuse-tail sharpness turns out to matter by ear, the lever is the reflection *type*, not
the order: `CONVOLUTION` keeps the whole response in the Ambisonic domain where order applies,
at materially higher cost than `HYBRID`. Measuring that trade is a separate exercise.

## Final configuration: CONVOLUTION + Ambisonic order 2

Recorded as `QualityPreset.HIGHEST`, and now the default for both the library and the cave demo.

### CONVOLUTION over HYBRID — a correction to my own earlier advice

I had documented `HYBRID` as "usually the right answer for a large reverberant space", on the
reasoning that parameterising the late tail saves the cost of convolving it. **Measured, that is
wrong.** Hybrid pays for the convolution *and* the feedback network, and comes out more
expensive at every duration tested:

| duration | CONVOLUTION p95 | HYBRID p95 |
|---|---|---|
| 1 s | 221 µs | 284 µs |
| 3 s | 555 µs | 622 µs |
| 6 s | 1066 µs | 1138 µs |
| 10 s | 1764 µs | 1823 µs |

No crossover in that range, and the early-reflection structure is indistinguishable (crest
factor 3.86 for both, ~515 discrete early peaks each). Convolution's tail is *less* linear in
decay (r² 0.68 against 0.92) — which is the point: a real convolved response decays irregularly,
where a feedback delay network produces an artificially smooth exponential.

Confirmed by ear: convolution has the nicer tail, and `PARAMETRIC` is audibly glitchy. The
likely mechanism for the glitching is that the network is re-driven by simulated reverb times
that step at the simulation rate (~15 Hz) rather than cross-fading, unlike convolution which
interpolates between impulse responses. `PARAMETRIC` remains the right choice for distant or
background sources at roughly a fifth the cost.

The library defaults for `ReflectionEffect` and `SimulationSettings.reflectionType` are now
`CONVOLUTION`, and the `ReflectionEffectType` KDoc carries the measurement.

### Ambisonic order 2, with the evidence stated honestly

Under `HYBRID` the order made no measurable difference, and the user could not ABX it — which
is consistent, because hybrid's parametric tail cannot be order-dependent. Under `CONVOLUTION`
the whole response stays in the Ambisonic domain, and order 2 improves the reflected field's
directional spread in **every** arrival window: +6% early, +21% mid, +49% late, +17% tail.
That coherence of sign is the signal; the earlier hybrid measurement had mixed signs, matching
the noise control.

Cost: median 281 → 648 µs, p95 559 → 1227 µs. **2.3× per block**, 5.2% → 11.4% of a 512-sample
budget.

`QualityPreset.HIGHEST`'s KDoc states the strength of this evidence rather than overselling it:
consistent in sign, comparable in magnitude to the run-to-run variance of a stochastic ray
tracer, and not ABX-tested under convolution. It is the right choice when quality is the
priority; it is not a free win.

`QualityPreset.HIGHEST` / `BALANCED` / `ECONOMY`, each carrying the measured per-block cost and
a sources-per-core estimate, so the delivering agent does not have to re-derive any of it.

| preset | config | p95 per source | % of block | sources/core |
|---|---|---|---|---|
