# Steam Audio → Kotlin/FFM bindings — scope

Target: `afield.four.audio.steamaudio`, Kotlin/JVM, JDK 25+, Panama FFM.
Upstream: Steam Audio **4.8.1** (released 2026-02-11), Apache-2.0.

## Where this lives in Field

Folded into Field rather than kept as a submodule, following the Ceres and TetGen pattern: the
code is in Field's own tree and its build graph, and only the binaries are fetched.

| | |
|---|---|
| L1, jextract output | `src/jvmMain/java/afield/four/audio/steamaudio/raw/` |
| L2, the Kotlin API | `src/jvmMain/kotlin/afield/four/audio/steamaudio/` |
| Demos | `src/jvmMain/kotlin/afield/examples/steamaudio/` |
| Tests | `src/jvmTest/kotlin/afield/four/audio/steamaudio/` |
| The pin + notices + header | `native/steamaudio/` |
| Fetch script | `tools/fetch_steamaudio_natives.py` |

`./gradlew fetchSteamAudioNatives` unpacks this host's libphonon into `build/steamaudio`, verified
against `native/steamaudio/checksums.txt`. Nothing binary is committed.
`-PsteamaudioLibrary=<path>` overrides it, which is the escape hatch for a libphonon you built
yourself (Linux arm64 being the case that needs one).

Not wired into `check`, for the reason TetGen and Ceres are not: a fresh clone has no network
guarantee. The tests instead skip with a stated reason via `SteamAudioNatives.isAvailable`, so
`check` is green on a clone that has never fetched the binaries and honest about why.

`src/jvmMain/java` is compiled at release 24 to match `compileKotlinJvm`'s `jvmTarget`; Gradle
rejects a mismatched pair outright. FFM has been final since 22, so this costs the bindings
nothing.

## Measured facts about the API

- **216 exported functions** in `phonon.h`; jextract binds **216/216** (100%).
- **62 structs**, **26 enums**, **31 opaque handle types**, **13 function-pointer types**.
- **No unions, no bitfields, no `long double`, no varargs.** Only fixed-width scalars,
  fixed-size arrays, and pointers. `IPLsize` is the only platform-dependent type (8 bytes
  on every target we care about).
- **All 62 struct layouts are byte-identical** across `arm64-apple-macos`,
  `x86_64-apple-macos`, `x86_64-linux-gnu`, `x86_64-windows-msvc` and `aarch64-linux-gnu`
  (verified by diffing `clang -fdump-record-layouts-complete` across all five ABIs).
  → **One generated binding set works on every platform.** No per-platform codegen.
- `IPL_NUM_BANDS == 3` in the shipped binaries (confirmed at runtime).
- The object model is extremely regular: every audio effect has exactly 7 functions
  (`Create`/`Retain`/`Release`/`Reset`/`Apply`/`GetTailSize`/`GetTail`). 60 of the 216
  functions are `Retain`/`Release` pairs. This regularity is worth exploiting.

## Architecture

Three layers:

- **L0 `native/steamaudio/`** — pinned header + notices; the libs themselves are fetched. Done.
- **L1 `afield.four.audio.steamaudio.raw`** — jextract output, 77 files / 32.5k LOC,
  checked in, marked internal. Regenerated by a Gradle task, never edited by hand.
- **L2 `afield.four.audio.steamaudio`** — the hand-written idiomatic Kotlin API. This is
  the actual work.

Generated with **no `-l` flag**, so the lookup preamble is
`loaderLookup().or(defaultLookup())` — meaning we control loading via `System.load(absolutePath)`.
That is what makes jar-extracted natives possible; jextract's default `libraryLookup("phonon")`
would hard-fail since it only consults the OS loader path.

## Work breakdown

### 1. Native loading (`SteamAudioNatives`) — small, fiddly
Detect os/arch → extract from classpath resource to a checksummed cache dir → `System.load()`
the absolute path. Must handle: repeat loads in one JVM, multiple classloaders, read-only
temp dirs, and an override for loading from a plain directory.
Windows additionally needs `TrueAudioNext.dll` + `GPUUtilities.dll` resolvable *before*
`phonon.dll` — load order matters.

### 2. Handles and lifetime — medium, this is where the bugs live
31 opaque types. The C convention is that `Create` takes `IPLXxx*` out-param and
`Release` takes `IPLXxx*` and **nulls the caller's slot**, so each wrapper needs to own a
stable 8-byte slot, not just a pointer value.
Design: `sealed class SteamAudioObject : AutoCloseable`, deterministic `close()`, plus a
`Cleaner` safety net. Refcount semantics (`Retain`) exposed only where the API genuinely
needs shared ownership (e.g. `IPLScene` held by both simulator and static meshes).

### 3. Enums and flags — small, but two real traps
- 5 flag-style enums (`IPLContextFlags`, `IPLDirectEffectFlags`, `IPLSimulationFlags`,
  `IPLDirectSimulationFlags`, `IPLReflectionsBakeFlags`) must be `@JvmInline value class`
  with `or`/`in` operators — **not** `enum class`, they're bit-OR'd.
- `IPLSIMDLevel` has **aliased values**: `IPL_SIMDLEVEL_NEON == IPL_SIMDLEVEL_SSE2 == 0`.
  A naive `fromValue` map collides. Needs explicit handling.

### 4. Structs — medium, split by call frequency
- *Cold* (settings, created once): Kotlin `data class` + `writeTo(MemorySegment)`.
- *Hot* (`IPLBinauralEffectParams`, `IPLDirectEffectParams`, `IPLSimulationInputs`, …,
  written every audio block): **must be zero-allocation**. Arena-backed mutable views with
  `var` properties writing straight through to native memory. No boxing, no per-block alloc.
- `IPLVector3` / `IPLCoordinateSpace3` / `IPLMatrix4x4`: small value types + read/write helpers.

### 5. `IPLAudioBuffer` — medium, and the most performance-critical piece
`{ int numChannels; int numSamples; float** data; }` — deinterleaved, caller-allocated.
Design: one contiguous arena-allocated sample block plus a channel-pointer array, wrapped as
`AudioBuffer`. Bridges to `FloatArray` / `FloatBuffer`. Reuse the SDK's own
`iplAudioBufferInterleave` / `Deinterleave` / `Mix` / `Downmix` / `ConvertAmbisonics` rather
than reimplementing them in Kotlin.

### 6. Callbacks (upcalls) — medium, risky in one place
13 function-pointer types via `Linker.upcallStub`. Two very different tiers:
- Cold: `IPLLogFunction`, `IPLProgressCallback`, `IPLAllocateFunction`/`FreeFunction`.
- **Hot**: `IPLClosestHitCallback` / `IPLAnyHitCallback` / their batched variants, for
  `IPL_SCENETYPE_CUSTOM`. These are invoked from Steam Audio's *own* ray-tracing threads at
  very high rates. Cost of JVM thread attachment and upcall overhead is the concern; must be
  allocation-free. If custom scenes aren't needed, this tier can be deferred cheaply.

### 7. Real-time safety surface — small, mostly design + docs
`iplSimulatorRunReflections` / `RunPathing` are blocking and must never touch the audio
thread; the `*Apply` calls are the audio-thread-safe subset. The Kotlin API should make that
split obvious rather than leaving it to documentation.
Note `IPLAudioEffectState` (`TAIL_COMPLETE`/`TAIL_REMAINING`) returned by `*Apply` is **not**
an error code and must not be thrown on — unlike `IPLerror`, which should throw
`SteamAudioException` on cold paths.

### 8. JPMS `module-info` — small, but the real "JVM 25 and above" ask
JDK 25 *warns* on restricted native access from the unnamed module; this is scheduled to
become *denied by default*. Shipping a named module lets consumers write
`--enable-native-access=afield.four.audio.steamaudio` instead of `ALL-UNNAMED`. Worth doing now.

### 9. Tests + CI — medium
- Create/release lifecycle test per handle type, with a counting custom allocator to assert
  zero leaks.
- **Layout-guard test**: assert generated layouts against the checked-in reference table
  (`src/test/resources/phonon-4.8.1-layouts.txt`, 62 records) so a future jextract or SDK
  bump can't silently shift a field.
- Golden-output test: run a binaural effect over a known impulse, compare to a stored buffer.
- CI across macOS / Linux / Windows.

## Decisions I need from you

1. **API scope.** Bind all 216, or start with a core subset? A natural first cut is to defer
   the GPU/accelerator paths (`Embree`, `RadeonRays`, `TrueAudioNext`, `OpenCL` — ~18
   functions) and the bake/probe system (`ProbeArray`, `ProbeBatch`, `ReflectionsBaker`,
   `PathBaker` — ~24 functions), leaving ~174 for the first pass. L1 binds everything
   regardless; this is only about how much of L2 gets a hand-written wrapper.

2. **linux-arm64.** Valve ships **no aarch64 Linux binary** — only `linux-x64` and
   `linux-x86`. So "all three platforms" currently means macOS (universal x64+arm64),
   Windows x64, Linux **x64 only**. Options: (a) accept that, (b) build libphonon from
   source for aarch64 (it's Apache-2.0 + CMake, but a real side quest). I verified the
   struct layouts already match aarch64-linux, so the bindings are ready either way.

3. ~~**Natives packaging.**~~ **Decided: fetch-on-build.** Nothing binary is committed. The
   release zip is pinned by SHA-256, as is every file taken out of it, and only this host's
   platform is unpacked. The zip is cached by `tools/native_download_cache.py` outside the build
   directory, so `clean` costs a re-extract rather than a 173 MB re-download. Classified
   artifacts remain the right answer if these bindings are ever published outside Field.

4. **Layer 2: hand-written or generated?** Given how regular the API is (that uniform
   7-function effect pattern), a small codegen pass over the header could emit most of L2
   mechanically, with hand-written overrides for `AudioBuffer`, `Simulator` and `Scene`.
   Cheaper to maintain across SDK bumps; more upfront work than hand-writing.

## Notes / gotchas already banked

- `IPLEmbreeDeviceSettings` and `IPLRadeonRaysDeviceSettings` are `typedef void` in the
  shipped configuration (they're only real structs when those backends are compiled in).
  jextract skips them; their parameters are just `void*` — pass `NULL`.
- `IPLCALL` is `__stdcall` on `_WIN32`. Harmless for us: on Win64 `__stdcall` is the standard
  x64 convention. It would be a blocker only for 32-bit Windows, which JDK 25 doesn't ship.
- The dylib exports 362 `ipl*` symbols but only 216 are declared in the public header. We
  bind the declared 216; the rest are internal.
- `phonon_interfaces.h` is a C++ header (`namespace api`, virtual classes). Irrelevant to
  FFM — ignore it.
- macOS `libphonon.dylib` is a universal binary (x86_64 + arm64), so one file covers both Macs.

## Target use case (drives Layer 2 priorities)

Full-quality spatial audio for a **lively, reverberative, cave-like space**: HRTF binaural
output, and a **dynamic arrangement of planes** that reflect and absorb, with sources acting as
sonic probes radiating into largely empty darkness.

That pushes the following to the front of Layer 2, ahead of the rest of the surface:

1. **`Simulator` / `Source` with an explicit thread split.** `iplSimulatorRunReflections` is
   the expensive blocking call and must live on its own thread, never the audio callback.
   The API should make that split structural rather than a documentation note.
2. **Dynamic geometry.** `InstancedMesh.updateTransform` + `Scene.commit` is the per-frame
   path for moving planes; `StaticMesh.add`/`remove` for appearing and disappearing ones.
   `commit` cost is what will bite, so it needs to be explicit and batchable — one commit per
   frame covering many plane moves, not one per plane.
3. **Reflections at quality.** `CONVOLUTION` and `HYBRID` reflection types, long `maxDuration`,
   high ray counts, plus `ReflectionMixer` to keep per-source convolution affordable.
4. **Tail handling as a first-class concern.** In a long-decay space, `getTailSize` / `getTail`
   are not an afterthought: when a source stops or a plane moves away, the tail must flush
   correctly or the reverb audibly truncates.
5. **The full binaural chain.** Direct → `BinauralEffect`; reflections → Ambisonics →
   `AmbisonicsDecodeEffect` in binaural mode. Both need to run allocation-free per block.

Two consequences worth recording:

- **Baking and probes are largely inapplicable here.** Baked reflection data assumes static
  geometry; with planes moving every frame, reflections must be simulated live. Probes/baking
  still get bound (full surface was requested), but they are not on the critical path — the
  exception being a static outer shell, if the space has one.
- **A quad/plane helper earns its place in the API.** The geometry primitive in this world is a
  four-corner plane with a material, not a general mesh, so `StaticMesh.plane(...)` and a
  material palette are worth having as first-class conveniences.

**Verified by direct measurement**, not by assumption (`./gradlew hrtfProbe`): impulse response
per azimuth gives ILD **+17.7 dB at +90°** / **−17.5 dB at −90°**, ITD peaking at
**600–690 µs** (the physiological range), ±90° mirrored, and ~0 for both at 0°/180°.
Energy spread across 24 azimuths is 5.1 dB.

A note worth keeping, since it bit the first version of the demo: **broadband ILD is a
frequency-dependent cue and aggregate RMS hides it.** The orbit render measures 3.9 dB of
broadband ILD but 1.7 dB below 500 Hz, 10.9 dB at 0.5–2 kHz, 14.0 dB at 2–6 kHz and 19.4 dB
above 6 kHz. A source that is all low-frequency energy will localise weakly no matter how
correct the HRTF is — demo and test signals need high-frequency content.

### Two things worth keeping

**A parked panel was sitting on the source corridor.** The first cave render showed the direct
path collapsing 39 dB partway through the *distance* movement. Steam Audio was correct: my
resting-panel layout put a 5x5 concrete slab at exactly `(0, 1, −9)`, and the receding source
passed behind it. Diagnosed by computing panel positions against the source path, not by
guessing. `panelTransform` now keeps all four panels off the `x = 0` corridor and occlusion is
confined to movement 4, where it is the subject.

**Analysis windows have to match the physics being measured.** Three separate times, a
measurement looked like a bug and was not: broadband RMS hid frequency-dependent ILD in the
orbit demo; a 30 ms "direct" window caught the 21 ms floor reflection; and a 30–60 ms "early"
window missed panel reflections entirely because geometry at 2.8 m reflects within 9 ms and
fuses with the direct arrival. In every case the audio was right and the measurement was wrong.

**Direct path carries no propagation delay.** Steam Audio's `DirectEffect` applies gain and
spectrum but not time-of-flight, while `ReflectionEffect` honours the simulated `delay`. So
direct arrives at HRTF latency (~6 ms) while reflections arrive late. This is the upstream
idiom, not a binding bug — but an application wanting true time-of-flight on the direct path
must add that delay itself.
