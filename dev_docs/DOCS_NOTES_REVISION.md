# Documentation notes as a revision queue

You write notes on the rendered documentation. Agents later revise the Markdown behind them,
one agent per page, in parallel, and nobody has to be in the room when it happens. This page
covers how a note finds its source lines, how it keeps finding them after the file changes,
and how the harness divides up the work.

The pieces:

| piece | file |
| --- | --- |
| the panel you write notes in (`/field-docs/…`, `Ctrl+Shift+A`) | `src/commonMain/resources/docsAnnotations.js` |
| the store and its routes | `src/jvmMain/kotlin/afield/server/docsAnnotations.kt` |
| sync, queue, briefs, outcomes, and the harness | `tools/docs_notes.py` |
| the build commit the panel stamps on each note | `field-docs-build.json`, written by `tools/build_zensical_docs.py` |
| security of the route that launches agents | [`DOCS_IMPROVEMENT_AGENT.md`](DOCS_IMPROVEMENT_AGENT.md) |

## The loop

```bash
# what is waiting, grouped the way the harness will split it up
uv run python tools/docs_notes.py queue

# the plan, without running anything
uv run python tools/docs_notes.py revise --dry-run

# one agent per page, four at a time; one commit per page once they have all finished
uv run python tools/docs_notes.py revise --jobs 4 --commit

# what one agent would be told about one page
uv run python tools/docs_notes.py brief public/docs/sound_paths.md
```

`revise` runs `sync`, partitions the queue, starts the agents, applies what they recorded to the
store, commits if you asked it to, and then runs `sync` again so every note, including the ones
just resolved, points at the new text. The welcome page's **Improve annotated docs** button runs
the same harness through `POST /api/docs-improvement`, with codex and without `--commit`.

## A note's states

| state | meaning | in the queue? |
| --- | --- | --- |
| `open` | a request nobody has finished | yes |
| `question` | an agent asked you something and nobody has replied | no, until you answer in the panel or with `reply` |
| `resolved` | an agent (or you) fixed it; `resolution` says how | no; `reopen` puts it back |
| `memory` | a note an *agent* left on a page, for the next agent | never |

Each note carries a `thread`: your replies, an agent's questions, resolutions and memories, and
a `run` entry when an agent was given the note and left no outcome. The `question` state is not
stored anywhere. It is worked out from the thread: a `question` entry with no `reply` or `reopen`
after it. So a reply is enough to put the note back in the queue.

Memories come in two kinds. An agent can attach one to the note it worked on
(`resolve … --memory "…"`, or `memory <id> "…"`), or leave one on the page
(`memory --page <page> "…" [--line N]`), which is stored as a `kind: memory` note. The brief for
a page includes every memory left on it, whatever state its note is in, along with the last few
resolutions, so that one agent does not undo another's work. Memories are for things the next
agent would otherwise have to rediscover: a constraint, a trap, the reason a sentence is worded
the way it is. A memory that only restates a change is noise.

## Finding the source

`sync` turns a note's `pageUrl` into a file (`reference/source/…` pages map back to the Kotlin
they mirror; pages headed `DO NOT EDIT — generated by …` are marked as generated) and then looks
for the note's quote in that file.

The quote was selected in rendered HTML, so it is matched against a *projection* of the Markdown:
the text a reader sees, with a map from each character back to its source offset. Links keep
their text, and emphasis, backticks, HTML, attribute lists, block markers and fence delimiters are
dropped. Whitespace and curly quotes are normalised. Matching goes exact, then case-folded, then
fuzzy (a `difflib` window with a ratio of at least 0.6). When the quote occurs more than once, the
recorded prefix, suffix and heading pick the right occurrence. That matters more than it sounds:
one of the two real notes in the store when this was built quotes the single word `Field`.

For a generated reference page, the quote is looked for in the KDoc of the Kotlin files that
contain its longest word trigrams (`git grep`), with ` * ` comment markers stripped. The note is
anchored there, so the agent edits the KDoc and not the generated page.

**The text the human read is the text that gets matched.** The docs build writes the commit it was
built from into `field4/field-docs-build.json`. The panel copies that into the note's
`anchor.sourceCommit`, and the server records its own `HEAD` as `recordedAtCommit` as a fallback.
`sync` matches against `git show <commit>:<page>.md` before it tries the working tree. That way a
note written on Monday and synced on Friday lands on Monday's sentence and is then carried forward
to where that sentence is now.

## Carrying a note forward: `git blame` origins

A note is anchored to its lines as the list of `(commit, path, line)` origins that
`git blame --line-porcelain -M` assigns them. An unchanged line keeps its origin however much the
rest of the file is edited, so to find the note later, `sync` blames the current working tree and
looks those origins up again. The status then says what happened:

| status | what happened |
| --- | --- |
| `anchored` | first association, or lines unchanged since |
| `exact` | still the same lines at the same numbers |
| `moved` | same lines, different numbers or a renamed file (renames followed with `git diff -M`) |
| `edited` | some anchored lines survived and some were edited; the range covers the survivors |
| `reanchored` | every anchored line was edited, but the quote still reads in today's text; `previousExcerpt` keeps what was there before |
| `orphaned` | lines gone and quote gone; `lastKnown` says where it was |
| `unanchored` | never found: no source file, a quote that is captured output rather than source text, or a position-only note |
| `uncommitted` | found only in uncommitted text, which has no origins yet; the next `sync` after a commit fixes it |

Two consequences are deliberate. Text search would put a note on the *first* copy of a sentence
that appears twice; identity puts it on the one that was annotated
(`test_the_same_sentence_elsewhere_does_not_capture_the_note`). And `-M` means a paragraph moved
within its file carries its note along. The cost is that a *copy* of an anchored line can share
the original's origin, so hits are split into runs, and the note stays with the run holding the
most of its lines, or the one nearest its old position when two runs tie.

After every sync the origins are re-based onto the current blame. The next sync then tracks from
today's lines, and a note resolved by rewriting its sentence follows the rewritten sentence.
`source.history` keeps the last twelve positions.

## Partitioning

One partition per page, with one exception: two pages whose notes would edit the same file are
merged (union-find over page and file), so no file is handed to two agents at once. This mostly
happens with reference pages generated from the same Kotlin file. Partitions are scheduled
largest first.

Each agent gets a prompt naming the files it owns and the brief for its pages. The brief has live
line numbers and excerpts, the thread, memories and recent resolutions. The agent is told not to
commit, not to run Gradle or the docs build, and to record an outcome for every note through the
same CLI. Inside a run those commands write to the partition's journal
(`DOCS_NOTES_JOURNAL`), not the store, and they refuse a note id that is not in the partition.
When the agent exits, the harness applies the journal to the store under the lock. Sandboxed
agents cannot reach `~/.afield` at all, and parallel writers to one JSON file lose notes, so the
store is only ever written from the harness.

Everything for a run is kept in `.field-backdoor/docs-notes/runs/<run-id>/`: each partition's
prompt, complete log and journal, and `summary.json`.

With `--commit`, the harness makes one commit per page after every agent has finished. Committing
while others were still editing would hand the pre-commit guard their half-written files. Each
commit carries `Docs-Note: <id>` trailers, and the commit sha is written onto the resolution
entries. `--commit` refuses to start if anything is already staged, and `revise` refuses to start
if a file it would hand out already has uncommitted edits (`--allow-dirty` overrides that).

## The store is shared, and the schema is the contract

The server rewrites the whole store file from its own `DocsAnnotation` data classes, with
`ignoreUnknownKeys`, so a key the Kotlin side does not declare is dropped on the next panel save.
`tools/test_docs_notes.py` (`KotlinSchemaTest`) checks every top-level key and thread-entry key
the tool writes against the Kotlin declarations, and every anchor key the panel sends. Detail only
the tool understands goes inside `source`, which the server keeps as an opaque `JsonObject`. A
panel save *merges* into an existing note: it keeps thread, source and resolution, and clears
`source` only when the anchor itself moved. `DocsAnnotationThreadTest` pins that against a file
written the way the tool writes it.

Both sides take a POSIX record lock on `<store>.lock` (`fcntl.lockf` and `FileChannel.lock`)
around every read-modify-write.

## What it does not do

- **It does not verify.** The harness does not build the docs or run the capture runner, because
  parallel agents would only queue on the verification lock. After a run, build the pages it
  touched (`build_zensical_docs.py --page …`) before you trust them. Anything that generates
  pages is listed at the end of the run, with the command that regenerates it.
- **Agents share one checkout.** Ownership is by instruction. The harness compares
  `git status` before and after and reports any change outside every partition's files, but it
  cannot tell which agent made it, and it never commits one.
- **Quotes from captured output do not anchor.** A sentence the docs runner printed is not in the
  Markdown. Those notes stay `unanchored`, with the page as their location, and the agent is
  handed the page.
- **The projection is approximate.** Tables, footnotes and HTML-heavy pages match fuzzily or not
  at all. `sync` prints each note's status, so check for `unanchored` before a long run.
- **Claude runs with a fixed allowlist**: `Read`/`Edit`/`Write`/`Glob`/`Grep`, the notes CLI,
  and read-only `git`/`grep`. Codex runs in `--sandbox workspace-write`. Use
  `--agent-command '… {prompt_file}'` for anything else.
